# 并发策略

> **一句话结论**：并发用「**进程内 subagent**」；外部多进程**最多 2 路**。

---

## 一、为什么这是个问题

Antigravity **支持并发** —— 它本身是多线程异步架构，并提供了官方的并行 Subagents 机制。

但**实现并发的方式有两种，可靠性差别很大**：

| 方式 | 进程数 | 可靠性 |
|---|---|---|
| **进程内 subagent** | 1 | ✅ 可靠 |
| 外部多进程 | 2 | ⚠️ 可用但有风险 |
| 外部多进程 | ≥3 | ❌ 概率性失败 |

---

## 二、三种方式对比

| 方式 | 做法 | 结论 |
|---|---|---|
| **✅ 进程内 subagent（首选）** | 把可分解任务写进**一个** prompt，让它自己 fan out | 1 个进程内并行，**无状态竞态**、开销小、可审计 |
| ⚠️ 外部多进程 | 同时启动多个 `agy` 进程 | **最多 2 路**；**≥3 路禁止** |
| ❌ 外部 ≥3 路 | —— | 概率性失败 |

---

## 三、外部多进程的失败机理

**症状**：400 `INVALID_ARGUMENT`

```
tools[…].properties[period].enum[0]: cannot be empty
retryable: false
```

**机理**：多个进程争抢**全局 MCP 状态缓存**的写入，产生残缺的工具 schema，服务端拒绝该请求。

**关键性质**：

- **`retryable: false` 不代表"不能重试"** —— 它指的是"**同一请求原样重发无意义**"。**新建进程重跑可以自愈**。
- **隔离工作目录无法规避** —— 竞态发生在全局缓存层，不在工作目录层。
- **串行也会偶发**（历史观测约 8%）—— 见第六节。

### 实测梯度数据

| 并发路数 | 成功情况 |
|---|---|
| 2 路 | 2 / 2 ✅ |
| 3 路 | 2 / 3 |
| 5 路 | 0 / 5 |
| 5 路（隔离目录） | 1 / 5 |

**刻意隔离工作目录后仍然失败** —— 这排除了"目录冲突"这一假设，确认了竞态在全局层。

---

## 四、推荐做法：进程内 subagent

把可分解的任务写进**一个** prompt，让主 agent 自己 fan out：

```bash
agy -p "请用 subagent 机制并行完成三个独立子任务后汇总：
(1) 查询 A 的最新进展；
(2) 查询 B 的最新进展；
(3) 查询 C 的最新进展。
每个子任务独立完成后，最终用三行分别回答，每行标注对应编号。" \
  --output-format json
```

**优点**：

- 只有 **1 个 `agy` 进程** → 无全局缓存竞态
- 上下文开销小（无需重复加载系统提示与插件）
- 可审计（见第五节）

**注意**：

- **耗时较长** —— 实测 3 路约 400 秒。预估超过约 2 分钟时应考虑**后台执行**。
- 必须**明确要求汇总形式**（如"用三行分别回答"），否则可能只给汇总项。

---

## 五、验证「确实 fan out 了」

**纯凭 `response` 自述不足以采信** —— 它可能声称用了 subagent 而实际没有。

**可审计指纹**（三条同时满足）：

1. `~/.gemini/antigravity-cli/conversations/` 下新增**多个 `.db` 文件**
   —— 1 个主库 + **每个 subagent 一个独立子库**
2. 主库中存在载荷含 **`invoke_subagent` + `Subagents` 数组**的 `type=132` step
3. 子库各有**独立的工具调用轨迹**与各自的部署 prompt

**核查方法**见 [`verification.md`](verification.md) §7。

---

## 六、要不要重试？

**要 —— 且是必需的。**

| 场景 | 失败率 | 处理 |
|---|---|---|
| 外部 ≥3 路并行 | 高 | **不要这样做** |
| 严格串行 | 约 8%（历史观测） | **串行 + 自动重试 ≥3 次** |

**关键认知**：串行**只降低概率、并不免疫**。

早期曾把该 400 归因为"多进程争抢"，据此推断"串行即可免疫、此错误不必重试"—— 后续实测（严格串行 14 次调用中仍有 3 次命中）**推翻了这个结论**。

⇒ **正确姿态是「串行 + 失败自动重试 ≥3 次」。**

---

## 七、不受限的情形

需要澄清的是，受限的**只是「多个 `agy` 进程同时跑」**。

以下并行方式是**允许的**：

- 一个 `agy` 进程的**内部 fan out**
- 调用方**自身的其他工作**与一个 `agy` 进程并行

> 例：调用方并行启动多个自己的子任务，同时外派**单独一路**给 `agy` —— 这属于"1 个 agy 进程"，完全合规。

---

## 八、决策速查

```
需要并行 N 个子任务？
├─ N == 1  → 直接派
├─ N >= 2  → 优先用「一个 prompt + 进程内 subagent」
│              └─ 若必须多进程 → 最多 2 路，且每路串行重试 ≥3 次
└─ 无论哪种 → 事后按 verification.md 三层判据核验
```
