# 结果验收与内容核验

> 本文覆盖：三层成功判据、失败形态分类、补救措施、结构化输出解析、内容真实性核验，以及可追溯的实测数据。

---

## 一、核心原则

> **不可只看 `status` 与退出码。**

`agy` 在**执行失败时同样返回 `status: "SUCCESS"` 与退出码 `0`**。仅凭这两个信号判断成败，会把大量失败当作成功采信。

必须按**三层判据**逐层核验。

---

## 二、三层成功判据

| 层 | 检查什么 | 判据 |
|---|---|---|
| **① 调用层（硬信号）** | 模型**真的跑过**吗 | **`usage.total_tokens > 0`** —— 唯一硬指纹；等于 0 即未真正执行 |
| **② 交付层（完备性）** | 要求的东西**真的给全**了吗 | 要求的 N 段/结论**全部出现** |
| **③ 内容层（真实性）** | 给的东西**对吗、完整吗** | 结构完整 + 来源核验 |

**辅助信号（均不可单独作准）**：`response` 非空、`num_turns > 0`。

### ① 调用层

**`usage.total_tokens > 0` 是唯一可靠的硬指纹。**

等于 0 的两种情况，都意味着"模型没有真正执行"：

- **超时截断** —— 误传了 `--print-timeout` 且值过小（见附录 C-6）
- **执行异常** —— 网络、认证或其他错误导致未到达模型

### ② 交付层

判据是「**含中间态字样 ∧ 要求的最终产出未出现**」。

⚠️ **只见 `Waiting for…` 不等于失败** —— 有可能同一段里既有 Waiting 字样，又有真正的最终结果。必须核对**要求的产出是否实际出现**。

**另一种更彻底的层②失败**是「**被拒空回复**」：硬信号全过（`total_tokens > 0`），但 `response` 是空字符串。成因见第四节。

### ③ 内容层

- **结构完整性**：围栏成对 + **末句完整**
  ⚠️ **括号配对不足以判定截断** —— 实测存在"括号全配对但末句被截断"的情形。
- **来源真实性**：见第五节（这部分最容易失守）。

---

## 三、失败形态分类

实测归纳出四种，**前三种都会通过 `status` / 退出码检查**：

| 形态 | 表现 | 识别方法 |
|---|---|---|
| **① 超时假成功** | `status=SUCCESS`、`exit=0`，但 `total_tokens=0` | 检查调用层硬信号 |
| **② 中间态正文** | 硬信号全过，但 `response` 停在 `Waiting for ... to conclude.`，最终产出缺失 | 检查交付层 |
| **③ 被拒空回复** | 硬信号全过，但 `response` 为空串，计费照扣 | `len(response) == 0` |
| **④ 内容失真** | 结构完整、看着像真的，但内容是编造的 | 逐条核验来源（第五节） |

### 补救措施

| 层不通过 | 措施 |
|---|---|
| ① 调用层 | **串行重试**（≥3 次）—— 偶发失败占相当比例，重试是必要的 |
| ② 交付层 | 用 **`--conversation <id>` 续接**，要求它输出最终产出 |
| ③ 内容层 | 重派；或降级为「部分交付」并**显式标注** |

> **续接的语义（重要）**：续接**不是"取回子代理结果"**。
> 子代理**不跨进程存活** —— 进程退出后它已被停止。续接的本质是让**主 agent 自行重做/继续产出**。

## 四、被拒空回复：成因与处理

**成因**：headless 模式**无法弹出授权提示**。当 prompt 要求写文件或执行命令而该动作未授权时：

1. 该动作被**自动拒绝**（`denied_actions` 非空）
2. stderr 出现 `no output produced — a tool required the ... permission ... auto-denied`
3. 整个回合**返回空 `response`**

**但硬信号全部通过**：`status=SUCCESS`、`total_tokens > 0`、`exit=0`。**计费照扣**（实测一次 20 万 token）。

**处理分两路**：

| 场景 | 处理 |
|---|---|
| **任务只需文本** | 在 prompt 显式声明「你没有文件写入权限，不要尝试创建/写入/运行任何文件；完整内容以文本形式写入回复」→ 重派（实测重派 1 次即恢复完整交付） |
| **任务确需写盘** | 按 [`permissions.md`](permissions.md) §2.2/§2.8 精确授权 `write_file(<目录>/)`。**不要**用 `--dangerously-skip-permissions` |

> ⚠️ **同时注意反面**：空回复**也可能是假失败**。
> 有副作用的步骤可能**已经成功执行**了（详见 [`permissions.md`](permissions.md) §5）。
> ⇒ **有副作用的操作一律在系统层回检**（`ls` / `test -f` / `git status`）。

## 五、内容真实性核验（最关键）

### 5.1 它会声称未发生的事

实测：它自称"已完成创建并校验"，而目标路径**没有任何文件**。

⇒ **凡涉及"已创建 / 已修改 / 已完成"的自述，一律实际核验。**

### 5.2 检索类任务的高失真率（实测数据）

**实验**：派发一次文献检索任务，产出报告后**抽查 6 条来源**。

| # | 形态 | 细节 |
|---|---|---|
| ① | **DOI 根本不存在**（2 条） | 两个声称的 IEEE 期刊论文 DOI，在 DOI 系统中**查无此物**。但**格式毫无破绽、卷期页齐全、作者名完整，纯属拼凑 —— 肉眼无法分辨** |
| ② | **DOI 真实但内容被整体改写**（1 条） | 一个真实存在的数据集 DOI：实际是 **135 KB 的工程文件**，被描述成「12,852 组时序 + 50 维特征 + 已清洗矩阵」；许可也从 **CC0 写成 CC BY** |
| ③ | 对照：其他通道全真 | 同任务改用其他模型执行，抽查 **3/3 全部真实**，数值细节与原文逐字吻合 |

**失真率：3 / 6 = 50%。**

### 5.3 结论与定性

> **幻觉的 DOI 无法凭肉眼分辨。**

这不是"工具不好用"，而是**它的失败模式在检索类任务上特别隐蔽**：

- 格式完整 → 看起来专业
- 卷期页齐全 → 符合领域惯例
- 作者名合理 → 不易察觉

**通道可用，但不可不做核验直接用。**

### 5.4 强制要求

1. **凡引用必逐条核**
   检索类**不适用"抽样复核"口径** —— 实查 `https://doi.org/<doi>`、`https://arxiv.org/abs/<id>`。
   **未通过实查的条目不得进入任何交付物**，只能降级为「来源存疑」并显式标注。

2. **禁止拼凑条款必须原文写进 prompt**（模板见 5.5）。

3. **数据集类须实查规模 / 文件格式 / 许可协议**，不得采信其转述。

4. **失真率不可接受 → 整路作废重做**（换用其他模型或通道），并在交付物中注明原因。

### 5.5 prompt 模板

照抄进检索类任务的 prompt 末尾：

```
来源纪律（强制）：
- 严禁拼凑 DOI：每一个 DOI 必须是你确实检索到并能确认字符级正确的；不能确认就不写 DOI，
  改写为「作者+年份+期刊+标题，DOI 待核」。
- 严禁转述失实：数据集的规模、文件格式、许可协议必须来自实际页面，不得推测或美化。
- 检索不到可信来源就明说「未检索到可核验来源」——这是正贡献，不算失败。
```

**设计要点**：最后一条很重要 —— 明确告诉它"承认检索不到"是**正贡献**，而不是失败。否则模型倾向于"编一个"来避免交白卷。

### 5.6 成本对比

**核验成本远低于返工成本。**

在上述实验中，正是因为做了核验，才及时发现整条通道的产出不可用并重做；**若跳过核验，虚构来源会直接进入交付物** —— 而这类错误在下游极难发现。

## 六、结构化输出解析

### 6.1 解析顺序

**优先读 `structured_output`** —— 这是 CLI 外层字段，是**已解析好的合规 dict**，不含 `toolAction` / `toolSummary` 等元字段。

```python
d = json.loads(stdout)
result = d.get("structured_output") or json.loads(d["response"].strip().splitlines()[-1])
```

| 解析路径 | 评价 |
|---|---|
| ⭐ `structured_output` | **最优** —— 已解析、零元字段 |
| `response` **最后一行** | **稳妥兜底** |
| 整段 `json.loads(response)` | ❌ **不可依赖** |

**为什么取"最后一行"是对的**：`response` 的形态**不固定**，可能是：

- 「正文 + 末尾一行紧凑 JSON」，也可能是
- 「单行纯 JSON」

取最后一行在**两种形态下都正确**。而整段解析会在第一种形态下因前导正文而失败。

### 6.2 条数由 prompt 决定

`--json-schema` 中定义的 `items` **条数不由 schema 决定，而由 prompt 决定**。

不显式要求"N 条"时，可能只返回 **1 条汇总项**，而真实明细留在正文里。

⇒ **需要 N 条就在 prompt 里写明 N 条。**

### 6.3 根节点必须是 OBJECT

`--json-schema` 的根节点如果是 `array`，会直接返回 400：

```
only allowed for OBJECT type
```

⇒ 需要数组时，包一层对象（如 `{"items": [...]}`）。

## 七、审计与回溯

所有调用都可完整回溯：

| 路径 | 内容 |
|---|---|
| `~/.gemini/antigravity-cli/scratch/` | 默认工作目录（其自主产物落此，不污染调用方目录） |
| `~/.gemini/antigravity-cli/brain/<会话id>/` | `plan.md` / `walkthrough.md` |
| `~/.gemini/antigravity-cli/conversations/*.db` | **SQLite：每轮 prompt 原文 + 逐 step 工具调用 + 权限拒绝记录** |

### 7.1 读取会话库

```python
import sqlite3, pathlib

db = pathlib.Path.home() / ".gemini/antigravity-cli/conversations/<会话id>.db"
con = sqlite3.connect(f"file:{db}?mode=ro", uri=True)

for idx, st, status, payload in con.execute(
        "SELECT idx, step_type, status, step_payload FROM steps ORDER BY idx"):
    print(idx, st, status, bytes(payload or b"")[:200])
```

### 7.2 关键字段语义

| 项 | 含义 |
|---|---|
| `step_type=132` | **通用「工具调用」step** —— 载荷可能是 `invoke_subagent`、`search_web`、`run_command` 等 |
| `step_type=101` | **子代理/系统消息回传** —— 仅当主回合**等到子代理回收**时才出现在主库 ⇒「主库有无 N 条 101」可作为**中间态的库层判据** |
| `step_type=14 / 15` | 用户输入 / 模型消息 |
| `status=7` + `error_details` | **被拒记录的落点**（注意：不是 `permissions` 列） |

### 7.3 审计的实用价值

- **验证"是否真的 fan out"** —— 见 [`concurrency.md`](concurrency.md)
- **定位权限拒绝** —— 查 `status=7` 的行
- **回查 prompt 原文** —— 用于核验"独立性"（如第二意见场景中，确认派出前我方意见未被泄露）
